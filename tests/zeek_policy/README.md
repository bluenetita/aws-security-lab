# Offline Zeek policy regressions

These tests exercise the recovered `blue-team/zeek/site/blueguard_exfil/`
policy on Zeek **9.0.1**. They use direct synthetic Zeek events and generated
PCAPs; they do not capture traffic, contact a live system, or prove detection
effectiveness. No generated script, PCAP, or Zeek log is written to the
repository.

## Prerequisites and commands

- Run on Linux/WSL as a **non-root** user with Python 3.12 or later and Zeek
  9.0.1, including its bundled base and policy scripts. The commands below
  assume the repository root; from elsewhere, pass an absolute path to `-s`.
  The tests resolve policy paths from their own file location.
- The default executable is `/opt/zeek/bin/zeek`. Set `BLUEGUARD_ZEEK` to a
  different **absolute** executable path if needed. A missing executable,
  other Zeek version, root execution, parse error, timeout, or nonzero Zeek
  exit fails clearly. No package installation is performed.
- Zeek reads only generated PCAPs with `-r`; test processes set
  `ZEEK_DNS_FAKE=1`. The generated PCAPs have zero checksums, so packet tests
  invoke Zeek with `-C`. The script runner uses `-D` for deterministic seeds
  and `-a` for parse/load validation.

From the repository root in Ubuntu WSL:

```bash
python3 -B -m unittest discover -s tests/zeek_policy -p 'test_*.py' -v
```

The corrected BG-BUG-003 host and destination acceptance tests are included
in that normal discovery command. The existing host-pipeline checks can be
run independently:

```bash
python3 -B -m unittest discover -s tests/host_pipeline -p 'test_*.py' -v
```

Before M3.4e, `test_bg_bug_003.py` had a separate reproduction command that
failed twice: new host and destination identities remained
`capacity_exceeded` after 80 synthetic minutes. Those cases now assert the
specific admitted identity, fresh profile history, and queued sample. The
reduced one-profile limits exist only in test scripts. Other boundary fixtures
temporarily use limits of two or a 120-second expiry; none changes the
laboratory's 60-minute configured default.

## BG-BUG-003 lifecycle and audit

Adaptive `profiles_host` and `profiles_dest` retain independent
`last_observed_active` timestamps in Zeek network time. A real window callback
with `flows > 0` refreshes an **existing** profile even if quality is degraded,
learning is suspended, volume is excluded from training, or payload is zero.
Idle and synthetic Slow zero-fill callbacks do not refresh activity. An
untracked callback still creates a profile only when existing baseline logic
adds a sample. The source-wide `learning_suspended_until` hold remains
independent of profile expiry.

At the Adaptive `window_tick_complete` barrier, after real callbacks and Slow
processing, profiles expire when `tick - last_observed_active >=
profile_idle_expiry`. The laboratory default is **60 minutes**. Host and
destination entries expire independently. Keys are collected before deletion.
No admission-time eviction occurs: an identity blocked during the expiry tick
can enter on a later callback. Expiration occurs before delayed sample
confirmation. If the configured interval is zero or negative, Zeek emits a
warning and **disables expiration**, retaining capacity limits rather than
evicting everything.

The existing `data_exfil_baseline` JSON field set is unchanged. Event-specific
field meanings are:

| `event_type` | `ts` | `original_sample_ts` | `sample_count` / `sample_bytes` |
| --- | --- | --- | --- |
| `exfil_baseline_commit` | Confirmation tick | Original sample window | One confirmed sample / its estimated bytes |
| `exfil_baseline_discard` | Discard time | Same discard time for the existing aggregate record; it is **not** a per-sample original timestamp | Pending samples discarded / sum of their estimated bytes |
| `exfil_baseline_profile_expired` | Expiration tick | Last observed active-window timestamp | Confirmed history entries retired / sum of their estimated bytes |

Pending samples are discarded with reason `profile_idle_expired` before the
separate profile-expiration record is emitted. Neither record means payload
delivery or real-world exfiltration. Readmission begins with fresh history and
is still subject to an unexpired source-wide learning hold.

The one-profile acceptance fixtures probe at 80 minutes, beyond the existing
30-minute window-host idle timeout, 35-minute slow-profile expiry, 15-minute
adaptive confirmation delay, and 10-minute learning hold. This test horizon
does not calibrate the 60-minute laboratory default for production. A shorter
expiry can discard baseline history prematurely; a longer one can keep new
identities capacity-blocked. Capture gaps and missing completed connections
can also make observed activity differ from real traffic.
